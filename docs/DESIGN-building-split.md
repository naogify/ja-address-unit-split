# 建物名・階・部屋番号の分離方式 設計書

> **移管の注記**: この設計書は `naogify/overture-address-ja`（ブランチ `feat/initial-implementation`）から、建物分離を別リポジトリへ分割する際にそのまま移したもの。本文中の `normalize.ts` / `keyWithUnit` / `addrUnverified` / `NJA` などは元リポジトリ（正規化側）の用語・項目で、このリポジトリには含まれない。入力はこのリポジトリでは「番地より後ろの文字列」。`splitBuilding`（NJA 呼び出し込み）はこのリポジトリでは外した。


対象: `src/building.ts`（`splitUnitTail` / `splitBuilding`）。ブランチ `feat/initial-implementation`。
数字は手元にあるものだけ。**未測**と書いたものは測っていない。全件ランの数字は「最終修正の1つ前のコード」での値（最終版での再ランは中止、後任へ）。

## 0. 結論（先に）
- 分離は「NJA の `other`（番地より後ろ）を起点に、規則で棟・階・部屋・建物名を切る」方式。**NJA の fork は不要**。
- 精度優先。建物と確信できないものは `building` に入れず `unparsed` に残す（文字は捨てない）。
- **建物情報が取れる行は少ない**。番地まで届いた行のうち、建物・階・部屋・棟のいずれかが取れたのは Overture 10.5% / JFF 21.9%。**Overture×JFF で同じ `key` を持つ 255,177 組のうち、71.4%（182,138）は両側とも建物情報が無い**。この行は `keyWithUnit == key|||` になる。
- 建物名マスターは**効果が小さい**。A（照合して切る）は +0.2%（相対）、B（無い所に補う）は埋められる行が Overture 12.6% / JFF 6.7% あるが、**既存の建物と一致するのは約75%**で、25%は誤補完になる。B は鍵に入れない。

## 1. 境界の決め方
- 起点は NJA の `other`。NJA が番地まで取れた行（level 8）は `other` が番地より後ろそのもの。
- NJA が番地まで届かない行（level 2〜3）は、`other` 先頭の番地らしい数字列（`\d+(-\d+){0,3}`）を `addrUnverified` として切り、残りを分離に回す。
- **4段番地 `1-6-8-407`**: NJA の `addr` は3区切りまでしか返さない（全件で addr が4区切りの行は 0）。`other` の先頭に `-NNN`（3〜4桁）が残ったときだけ部屋とする（`hyphen4` 規則）。該当は Overture 31 件 / JFF 107 件。本物の4段番地を誤認する可能性は、`-NNN` が3〜4桁の場合のみ発動する点で抑えているが、**誤認率は未測**。
- `other` に何が残るか（Overture 標本、ローマ字行含む）: 階・部屋・建物名のほか、ローマ字町名の切れ端（`Kita 32 Jonishi`）、区名（`Chuo-ku`）、`付近`、番地の断片。これらは規則で `unparsed` に回る（建物扱いしない）。
- **NJA fork 不要の根拠**: `other` に番地が残るのは NJA の住所データに該当番地が無いケース（例: 丸の内1-5-1）で、パーサ欠陥ではない。それらは `addrUnverified` で拾える。実測した欠陥は1件だけ: **NJA が `other` 内の漢数字を数字に変換する**（`シエ-ル千島306` → `シエール1000島`、`一の宮ビル` → `1-宮ビル`）。標本150件中2件。NJA は両側で同じ変換をするので鍵の一致には影響しないが `buildingRaw` が原文と異なる。別 issue 候補（NJA 上流への報告 or 原文の suffix 復元）。

## 2. 建物名の検出（規則の優先順）
`master` → `suffix`（語尾辞書）→ `facility`（施設語）→ `latin-suffix` → `katakana`（4文字以上のカタカナ連）→ `floor-anchor`（階が付いた語尾なしの名前）。どれにも当たらなければ建物なし。
- **語尾辞書は実データの頻度から作成**（Overture 10万行の level 8 建物文字列 5,526 件）: ビル 2,160 / 内 189 / 館 173 / マンション 77 / ハイツ 71 / 店 97 / 会館 40 / プラザ 37 / 本館 24 / 号館 24 / 番館 17 / スクエア 16 / センター 17 / レジデンス 11 / コーポ 10 ほか。単独の漢字（町・区・山・田）は町名と紛れるので語尾辞書から除外。
- `floor-anchor`: 階（`3F` `2階`）が付いている場合、その前の名前（`ららぽーと横浜 3階` `Espoir Kanayama 1F`）は建物・テナント名の確度が高い。標本の見逃しの約1/4がこれだった。`店舗` `事務所` など一般語だけ、`CH.158` のような英字+ドット+数字、番地の食い残しは除外。
- 除外（`unparsed` へ）: `付近` `周辺` `地先`、漢字だけの `〇〇区` `〇〇町`、番地の食い残し（`\d+-\d+` や `町390`）、英字だけで建物語を含まない語（ローマ字町名）、施設語の前が1文字以下（`美園`）。
- カタカナの長音符が半角ハイフンで書かれる実データ（`コ-ポ` `グリ-ンコ-ト`）は `ー` に直してから判定。
- 外部の手がかり: JIGYOSYO の事業所名は `evidence.officeName`（別フィールド）に出す。KEN_ALL の `（…階）` 付き町域は `town.ts` でビル名＋階に分解済み。Overture `names` は使っていない（**未測・未実装**）。

## 3. 階・部屋・棟
- 階: `3F` `3階` `B1F` `B-1` `地下1階` `地下一階` `二階`（漢数字）`M2F` `中2階` `屋上` `RF` `3・4階` `3F-5F` `1・2F`。地下は負数。複数階は `floors`、原文は `floorRaw`。
- 部屋: `301号室` `101号` `#301` `Room 12` `No.5`、建物名直後の裸の数字（`〇〇ビル401`）、語尾なし名の末尾（`ソフィア上野301` `エスト京橋 1A`）、全体が裸の数字（`103`）、`1-A`、`B111`。
- **裸の数字は部屋とし、階は推定しない**。根拠: 「3階301号室」型の205件で 階=部屋÷100 が成り立つのは187件（91%）だが、鍵に推定値を入れると表記の有無で鍵が割れるため。必要なら `floorInferred` を別フィールドで足す（未実装）。
- 棟: `A棟` `3号棟` `東棟` → `wing`（`keyWithUnit` には入れない）。`3号館` `東館` は建物名の一部。
- 順序の揺れ: 部屋が先頭（`#501 リスペースワン`）、カンマ区切り、ローマ字、`/` `_` 区切りに対応。先頭に POI 名が来る形（`ツルハドラッグ 松本島立店, 松本市…`）は**未対応**。

## 4. 出力と `keyWithUnit` の正規定義
- `building`（表示用: NFKC・空白整理・ビルディング/ビルヂング→ビル）、`buildingRaw`（NFKC のみ）、`floor` `floors` `floorRaw`、`room` `roomRaw`、`wing`、`unparsed`、`evidence.unit.rules`（`building` = 規則名、`floor`、`room`）、`evidence.unit.hasUnit`。
- `keyVersion = 1`。`key` = `pref + city + town + addr`（区切りなし。`keyLevel === 'addr'` のときだけ強い鍵）。
- **`keyWithUnit = key + '|' + B + '|' + F + '|' + R`**
  - B = `normalizeBuildingName(building)`: 表示用正規化 → 空白・中黒・ハイフン・長音符・`|`・括弧を除去 → 英字大文字化 → ヶ/ヵ を ケ/カ
  - F = 階の整数（地下は負、無ければ空文字）
  - R = 部屋を NFKC・空白と `|` を除去・大文字化（無ければ空文字）
  - 建物情報が無い行は `key|||`。`wing` は含めない。
- **`evidence.unit.hasUnit` で建物情報の有無を判別**できる。名寄せ側（145）は `hasUnit=false` の行を「住所だけで同一とみなさない」判断の材料にできる。

## 5. 測定
全件ラン（最終修正の1つ前のコード。Overture 2,864,272 行 / JFF 1,359,867 行。9 プロセス並列、Overture 10.6 分・JFF 7.0 分）。「番地まで」= `keyLevel === 'addr'`。

| | Overture | JFF |
|---|---|---|
| 番地まで届いた行 | 1,792,735（62.6%） | 832,835（61.2%） |
| うち 建物あり | 160,898（9.0%） | 164,761（19.8%） |
| うち 階あり | 120,489（6.7%） | 132,708（15.9%） |
| うち 部屋あり | 27,227（1.5%） | 32,118（3.9%） |
| うち 棟あり | 1,154 | 1,522 |
| うち いずれか | 188,146（**10.5%**） | 182,022（**21.9%**） |
| うち unparsed が残る | 40,652 | 22,482 |

建物の規則別（番地まで届いた行）: Overture suffix 110,591 / katakana 24,789 / floor-anchor 12,020 / facility 10,141 / latin-suffix 3,357。JFF suffix 116,425 / katakana 21,689 / facility 13,775 / floor-anchor 12,083 / latin-suffix 789。部屋の規則: Overture bare-after-building 15,280 / token 7,602 / bare 4,314 / hyphen4 31。

**同一 `key` のペア（Overture×JFF、番地まで届いた行）**: key 1,353,937 種、両ソースにある key 255,177（行数 1,146,310）。そのうち 建物情報が片側以上にある 73,039（28.6%）、両側にある 26,421（10.4%）、**両側に無い 182,138（71.4%）**。→ 大半の同一住所ペアは建物情報が無く、鍵に建物を足しても区別できない。

**精度（標本の目視。シード固定、一部は修正前の版）**
- 修正前の版: 「検出した」150行を目視 → 建物の種類が誤り約3%（5件）、末尾に方角・記号・部屋が混入約6%（9件）、建物があるのに `unparsed` に落ちた見逃し約6%（9件）。「建物なし・tail あり」120行 → 実在の建物の見逃し約26%（階付き15%＋語尾なし11%）。これを受けて `floor-anchor` などを追加。
- 修正後の版（全件ランの出力から標本150）: 建物の種類が誤りは 0〜2件、混入は約7%（10件）、見逃しは1件。混入10件のうち8件を追加で修正済み（この修正後の再ランは未実施）。
- **JFF の標本目視は未実施**。標本300の枠（Overture 150＋120、JFF 0）は未達。後任へ。

**建物名マスター（国税庁 法人番号。建物語・階・号室を含む現存の所在地 557,683 行を同じパイプラインに通した。建物名 134,854 種、key 143,331 種、うち複数建物の key 19,258）**
- A（住所内の建物名をマスターで照合して切る）: Overture 888,912 行（全体の31%）で、建物あり 50,312 → 50,408（**+96、相対 +0.2%**）。減ったものは 0。増えた例はいずれも妥当（`あべのベルタ` `季一遊`）。**マスターの建物名自体が同じ規則で作られた循環があるため、実際の効果の上限に近い**。
- B（同じ番地で建物が無い行に、マスターから補う）: 建物が無い行のうちマスターに同じ key がある行 Overture 205,756（12.6%）/ JFF 44,526（6.7%）、候補が1つに絞れるのは 138,375 / 30,179。**既に建物がある行で、同じ key のマスター建物と一致するのは Overture 76.9% / JFF 74.6%**（一致=包含を含む緩い判定）。→ 約25%は別の建物。補うと誤補完になるので **B は `keyWithUnit` に使わない**。出すなら別フィールドの候補（`buildingCandidates`）で、利用者が選ぶ形。
- 法人番号は登記上の本店所在地で、POI の所在地と一致しない（自宅・空室・移転）ため、一致率の上限は低い。

## 7. 限界と引き渡し
- 建物情報が無い行（Overture 約90%、JFF 約78%）では `keyWithUnit == key|||`。扱いは名寄せ側の判断。部下145 の実測（鍵だけの名寄せは参照ペア 64.2%、名称<0.3 の100組のうち30組が誤統合）の通り、**雑居ビル・駅ビル・モールの別店舗は建物・階が取れない限り区別できない**。
- 145 が指摘した `県内一円`・ローマ字切れ端・区名のゴミは、`unparsed` に回る規則を入れた（`付近` `〇〇区` ローマ字語 番地食い残し）。**移動販売の `県内一円` の扱いは未測**。
- 未対応・未測: 先頭 POI 名、Overture `names` の利用、JFF の目視精度、`hyphen4` の誤認率、最終コードでの全件ランと鍵の安定性の再測定、README。
- NJA fork: **不要**（§1）。
